# Pi Agent Harness：目录结构、功能模块与核心代码走读

> 本文档深入分析仓库目录结构、各功能模块的职责与关键文件，
> 并沿启动链路走读核心代码逻辑（所有路径与行号均为分析时 `main` 分支实际情况）。
> 建议配合源码阅读：`packages/agent/src/agent-loop.ts` 与 `packages/ai/src/models.ts` 是理解全项目的两个支点。

---

## 1. 项目总览

Pi 是 MIT 开源的终端编码 Agent（CLI 命令 `pi`），npm workspaces monorepo，共 10 个包：

- 应用层：`packages/coding-agent`（CLI，四种模式）
- 运行时层：`packages/agent`（Agent Loop 等通用能力）
- 基础设施层：`packages/ai`（统一 LLM API）、`packages/tui`（终端 UI）、`packages/protocol` / `client` / `server`（远程会话）、`packages/telemetry`、`packages/session-backends/sqlite-node`、`packages/evals`

依赖方向：`coding-agent → agent → ai / tui`，各包可独立发布（npm 名 `@earendil-works/pi-*`）。

## 2. Monorepo 目录结构全景

```text

    ├── coding-agent/            # CLI 应用层（bin: pi）

    ├── ai/                      # 统一多供应商 LLM API
    ├── tui/                     # 终端 UI 库
    ├── protocol/                # CBOR 远程会话协议

    ├── server/                  # 实验性服务端

```

## 5. 核心代码逻辑走读

### 5.1 cli.ts —— 薄入口

```ts
process.title = APP_NAME;
process.env.PI_CODING_AGENT = "true";
configureHttpDispatcher();          // 任何 SDK 发请求前配置代理
main(process.argv.slice(2));
```

要点：入口只做环境标记与全局 HTTP 配置，逻辑全部下沉 `main()`。

### 5.2 main.ts —— 总编排（569-977 行）

`main()` 固定流水线：

1. `SettingsManager.create(cwd, agentDir)` 加载全局+项目设置（588）；
2. `handleAuthCommand`（578）：拦截 `/login`、`/auth` 等认证子命令；
3. `parseArgs` + `resolveAppMode`（609/640）：解析参数并决定模式（`interactive` / `print` / `json` / `rpc`）；
4. 创建 `AgentSession` runtime：内部组装 ModelRuntime、工具、扩展（约 700-870 行区间，含模型解析 `model-resolver`）；
5. **模式分发**（927-976）：

```ts
if (appMode === "rpc")        await runRpcMode(runtime);
else if (appMode === "interactive") { new InteractiveMode(runtime, {...}).run(); }
else                          await runPrintMode(runtime, {...});
```

要点：**四种模式共享同一 runtime 与模型解析，只是消费事件流的方式不同**。

### 5.3 agent-loop.ts —— 核心循环（95-225 行）

整个项目的心脏，双层 while 结构：

```ts
async function runLoop(initialContext, newMessages, config, signal, emit, streamFunction) {
  let pendingMessages = await config.getSteeringMessages?.();   // 排队消息（用户边等边输入）
  while (true) {                                                // 外层：队列驱动
    while (hasMoreToolCalls || pendingMessages.length > 0) {    // 内层：工具驱动
      const message = await streamAssistantResponse(currentContext, config, signal, emit, streamFunction);
      newMessages.push(message);
      const toolCalls = message.content.filter(c => c.type === "toolCall");
      if (toolCalls.length > 0) {
        // stopReason === "length" 时拒绝执行截断的工具参数（211-214）
        const executed = message.stopReason === "length"
          ? await failToolCallsFromTruncatedMessage(toolCalls, emit)
          : await executeToolCalls(currentContext, message, config, signal, emit);
        hasMoreToolCalls = !executed.terminate;
        currentContext.messages.push(...executed.messages);     // 工具结果回填上下文
      }
      await emit({ type: "turn_end", message, toolResults });
    }
  }
}
```

关键设计：

- **消息模型统一**：全程 `AgentMessage`（user/assistant/toolResult），只在调用 LLM 边界（`streamAssistantResponse` → `streamFunction`）转换为供应商 `Message[]`（`agent.ts` 的 `defaultConvertToLlm`）；
- **事件流驱动**：`emit()` 广播 `agent_start` / `turn_start` / `message_start` / `tool_call` / `turn_end` / `agent_end` 等事件，TUI、print/json、RPC 全部消费同一流；
- **工具执行双路径**：`executeToolCallsSequential`（411）/ `executeToolCallsParallel`（489），`prepareToolCall`（600）统一预处理（参数校验、输出累积）；
- **截断保护**：`stopReason === "length"` 时整批失败工具调用，防止执行被截断的参数；
- **可插拔流函数**：`StreamFn` 抽象，默认 `getDefaultStreamFn()`，可替换为任意传输。

### 5.4 model-runtime.ts + model-resolver.ts —— 模型裁决

- `model-runtime.ts`：`getAvailableSnapshot()` 只返回**已配置认证**的供应商模型；`hasConfiguredAuth(provider)` 检查 key/oauth 是否存在；
- `model-resolver.ts`（640-701）默认模型解析优先级：
  1. CLI 参数（`--provider` / `--model`）；
  2. `scopedModels`（会话恢复的模型列表）；
  3. `settings.json` 的 `defaultProvider` / `defaultModel`（需已配置认证）；
  4. 遍历内置 `defaultModelPerProvider` 表（**anthropic 排在 deepseek 前**，检测到认证即选中）；
  5. 兜底第一个可用模型。

> 这正是"残留 `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` 时 pi 误走 Anthropic 通道导致 403"的代码根源。

### 5.5 models.ts + providers/deepseek.ts —— 供应商抽象（链路尽头）

`models.ts` 的 `Provider` 接口（97-149 行）是统一契约：

```ts
interface Provider<TApi> {
  id: string; name: string;
  baseUrl?: string; headers?: ProviderHeaders;
  auth: ProviderAuth;                    // 必选：apiKey 或 oauth（决定是否"已配置"）
  getModels(): readonly Model<TApi>[];   // 同步模型目录
  refreshModels?(ctx): Promise<void>;    // 动态目录（按 ETag 增量刷新）
  stream(model, context, options);       // 核心：流式对话
  streamSimple(model, context, options);
}
```

注册样例 `providers/deepseek.ts`（六要素声明式）：

```ts
createProvider({
  id: "deepseek",
  name: "DeepSeek",
  baseUrl: "https://api.deepseek.com",
  auth: { apiKey: envApiKeyAuth("DeepSeek API key", ["DEEPSEEK_API_KEY"]) },
  models: Object.values(DEEPSEEK_MODELS),
  api: openAICompletionsApi(),           // 协议复用：多厂商共用 openai-completions 实现
});
```

设计：**协议实现（api）与供应商解耦**——60+ 供应商只声明"用哪个协议 + 认证 + 模型表"，这是 pi-ai 能覆盖海量供应商的关键。
